## Four bounded cases

- Success: original request ACK, real exported snapshot/full v2 proof, encrypted
  database/document custody, completed interval, actual V2 preparation/staging,
  durable common report and final root all succeed.
- Unknown final-root ACK: the synthetic server stores the final root and loses
  the response. The parent fails closed; the saved common report lets a fresh
  reader discover and verify the original final root.
- Unknown common-report readback ACK: the report is stored, but its exact original
  readback response is lost. No final root is written. A fresh reader learns the
  original pin, cannot verify a missing final root, and can inspect the exact
  prepared root without executing publication or repair.
- Unknown original-request ACK: the request is stored, but its original readback
  response is lost. Source/window/capture are not entered and no data keys or root
  are produced. Fresh discovery preserves requested-only uncertainty and refuses
  replay. This case deliberately does not run a database dump/proof.

Each case rechecks the same original control revision. Before fresh discovery the
original SQL holder disconnects; for cases that captured data, original local
full-proof dump/report files are removed from the protected disposable directory.
The fresh process objects receive only trusted control, journal/archive config and
epoch floor. They learn candidate bindings/root pins from the live-head bootstrap
and signed-interval root workflow, without locally supplied candidate ID or pin.
Fresh reconciliation performs no writes or data-key generation. A deliberate
repeated original request makes at most its refused conditional reservation; no
source execution, accepted object version or data-key generation is repeated.
