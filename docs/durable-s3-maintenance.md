# Required S3 evidence in managed maintenance

17 October 2026. Default internal `ManagedBackendMaintenance` uses protocol9 and
requires `ManagedS3MaintenanceEvidence` as its eleventh component. All earlier
read/write/signed/TUS controls remain mandatory. This is local source and
synthetic-provider integration, not activation of an actual supplier or a public
operator route. Full backend quiescence and reopening remain unproven.

## Plan and original shutdown boundary

The plan binds the explicit S3 mode, complete branch registry/custody/evidence
configuration and actual Supabase metadata configuration. Constructor scope
checks reject a substituted project, region, capture identity or writer registry.
An authentic protocol8 plan and an omitted S3 component refuse before dispatch.
No mode is guessed and no working-mode failure falls back to current-disabled.

The ordered source sequence is:

1. Acquire the original installation-wide conditional ATTEMPTED acknowledgement.
2. Save/pin original read, standard-write, signed-upload, configured ordinary-TUS
   and signed-TUS baselines through their existing independent barriers.
3. Obtain the selected original S3 baseline: every configured working key at both
   endpoints with encrypted original capabilities, or explicit current-disabled
   PRE evidence at both endpoints. Save/read back the independent public artifact.
4. Conditionally record the exact original `s3BaselinePin` in new S3_BASELINED
   control phase, after SIGNED_RESUMABLE_BASELINED; read back the acknowledged
   head and original public baseline before any shutdown dispatch.
5. Suspend/cancel services, close real database writers, invalidate passwords,
   close the reviewed storage access paths and revoke reviewed signing issuer.
6. Obtain all prior refusal reports plus the selected fresh S3 report, paired
   with the original S3 baseline. Record its exact pin and outer artifact SHA as
   `observations.s3ProofDigest` before OBSERVED_CLOSED. A final saved-report readback checks its exact digest and
   limits its age to180seconds before the bounded control-head commit; slow final
   metadata cannot silently refresh an old S3 result.

A lost canary, independent artifact, head publication or head readback ACK cannot
be reconstructed into execution authority. Before the S3 boundary it prevents
shutdown. After closure, a missing report/ACK leaves the parent at S3_BASELINED;
there is no automatic repeat, compensation, publication backfill or reopening.

## Control parsing and saved inspection

The independent head remains bounded to8192bytes. It stores original pins, not
large cohort artifacts. S3 public artifacts keep their branch-specific bounds;
the common head pin permits the131072-byte working manifest, while current mode
enforces its own16384-byte bound. S3_BASELINED requires every earlier baseline.
Final S3 pins/digest must be complete and the observation pin SHA must match the
recorded S3 proof digest. Early, wrong-attempt/revision/kind and repeated baseline
grants are refused. Missing S3 final evidence cannot pass current inspection.

Low-level parsing retains compatibility with narrower historical records; these
do not become protocol9 evidence. The default coordinator checks its exact new
plan and requires every current pin/digest before treating a closed record as
complete for this bounded observation. It cannot bypass S3 through an old phase.

Fresh inspection re-reads exact original S3 baseline/report versions and validates
the selected mode/pair/digest. It performs no S3 data probe, KMS operation, upload
or evidence publication. `recordedS3CoverageObserved` is separate from
`freshS3CoverageObserved:false`. Other already-established fresh metadata/read
checks retain their existing scope; saved S3 coverage never becomes fresh proof
or missing command acknowledgement.

## Local evidence

The54-test parent suite includes both complete S3 modes, required original-head
ordering, unknown canary/public/head/readback ACKs, missing originals, a stale
POST gateway, incomplete final pins/digests, illegal transitions and authentic
protocol8 downgrade refusal. Existing historical control and earlier capability
failure tests remain passing.

The disposable TLS PostgreSQL proof exercises39 scenarios: the legacy three-
service-plan guard and38 integrated cases, including previously enabled S3 with
two reviewed keys/four endpoint children and explicit already-disabled success.
All provider HTTP/S3/KMS transports are synthetic; role/session/password checks
are actual PostgreSQL. Before provider suspension it asserts S3_BASELINED and the
original pin. Before storage mutations it checks both real writer roles have
NOLOGIN and NULL passwords. The previously enabled case preserves the actual
S3-off PATCH ordering; already-disabled cases correctly need only legacy-key
closure and reviewed-key deletion. Saved inspection is checked for no active
S3/KMS/TUS/publication or control revision change after uncertain outcomes.
